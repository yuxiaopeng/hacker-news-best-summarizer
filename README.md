## 5. Using GCC's Nested Functions with Wide Pointers and No Trampolines II

**原文标题**: Using GCC's Nested Functions with Wide Pointers and No Trampolines II

**原文链接**: [https://uecker.codeberg.page/2026-07-14.html](https://uecker.codeberg.page/2026-07-14.html)

Martin Uecker's article discusses how to use GCC's nested functions without run-time trampolines, which are a security risk due to requiring an executable stack or inefficient heap allocation.

He provides two key updates:

1.  **GCC 16: Nested Functions Without Capture:** GCC 16 guarantees that nested functions which do not access variables from their parent scope will not require a trampoline. This behavior is now documented and consistent even without optimization. Such functions can be safely returned, and the compiler will issue warnings for obvious attempts to return functions that *do* capture context. They can still access static variables, named constants, or types.

2.  **GCC 17: Nested Functions with Capture:** A patch was merged into the development branch of GCC (likely for GCC 17) introducing new built-in functions: `__builtin_call_code_address`, `__builtin_call_static_chain`, and `__builtin_call_with_static_chain`. These built-ins enable nested functions that *do* capture parent variables to be used without trampolines. Under the hood, GCC transforms such code to pass the static chain via a special ABI-reserved register, effectively simulating manual boilerplate. The article demonstrates how to wrap these built-ins with macros (e.g., `wide`, `CLOSURE`, `CALL`) to create a cleaner syntax for "wide pointers" that encapsulate both the function code and its context. This method allows for significant compiler optimizations, as shown by an example optimizing to a single assembly instruction.

The outlook mentions future discussions on cross-compiler portability (Clang/GCC) and workarounds for older GCC versions.

**原文链接**: [https://www.derekthompson.org/p/the-american-sports-plutocracy-is](https://www.derekthompson.org/p/the-american-sports-plutocracy-is)

文章《美国体育财阀政治》指出，美国体育法律构成了一场“公开的阴谋”，使得富人无需建设或创新就能变得极其富有。作者以洛杉矶湖人队近期高达125亿美元的估值为例，认为球队老板通过简单地持有那些被法律体系人为地制造出稀缺性和盈利性的资产，就能获取巨额利润。

这一“美国体育阴谋”主要通过四种机制运作：
1.  **法律寡头垄断：** 体育联盟在很大程度上免受反垄断法的约束，使得现有老板能够限制球队扩张并集体协商转播权。这人为地制造了稀缺性，保护了特许经营权免受竞争，并稳定了收入。
2.  **劳动法例外：** 美国劳动法允许球队集体协商选秀和工资帽等雇佣条款，这通过确保竞争平衡来保护资产价值，从而使老板受益。
3.  **体育场馆补贴：** 地方政府经常通过免税债券等方式补贴体育场馆建设，尽管对公众而言经济回报存疑，但这实际上将公共资金转移给了私人老板。
4.  **球队老板的税收优惠：** 老板可以将球队收购成本在十年内进行摊销，这允许从应税收入中进行大额扣除，从而降低了即使是盈利球队的实际税率。

作者强调这种稀缺性是人为制造的，不同于艺术品的自然稀缺性，这暗示法律是可以改变的。尽管他承认某些联盟规则的复杂性以及球迷的偏好，但他认为现状“令人厌恶”。他提出了一些潜在的改进措施，例如限制税收摊销优惠，并允许地方政府持有他们资助的球队的股份，他总结说，虽然这个系统并非“作弊”，但法律本身“存在问题”。

## 9. Show HN: MCP-stama – 极速无依赖Rust MCP服务器

**原文标题**: Show HN: MCP-stama – An ultra-fast Rust MCP server with no dependencies

**原文链接**: [https://github.com/StamManif/mcp-stama](https://github.com/StamManif/mcp-stama)

**mcp-stama** is an ultra-fast, zero-dependency MCP (Multi-platform Context Protocol) server built in Rust, designed to provide local context to AI coding agents like Cursor and Claude Desktop. It addresses the inefficiencies of traditional Node.js or Python MCP tools, which consume 200MB+ RAM and have slow startup times (1-3 seconds).

In contrast, mcp-stama runs natively with a memory footprint of less than 10MB and delivers sub-millisecond tool response times (<2ms cold startup, 300µs – 5ms p50 latency). It's distributed as a single static binary, eliminating external runtimes and complex dependencies.

Key built-in, high-performance tools include:
*   `fast_grep`: Sub-millisecond file search and regex scanning using `ignore::WalkBuilder`.
*   `git_snapshot`: Pure-Rust Git inspection via `gix`, avoiding external Git executables.
*   `docker_watcher`: Instant Docker container and system diagnostics using `bollard` and `sysinfo`.

Installation is streamlined with one-command scripts for macOS/Linux and Windows, or via Cargo for Rust developers. An `auto-configurator` feature (`--install-cursor`, `--install-claude`) allows for automatic injection into editor settings. All communication is via pure Stdio JSON-RPC 2.0, with diagnostics routed to stderr. The project includes an embedded benchmark suite (`--benchmark`) and is licensed under Apache 2.0.
